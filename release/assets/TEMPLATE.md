# Release Notes 模板

> 本文件是 release skill 的 **内部参考模板**（`release/assets/TEMPLATE.md`），用于在用户项目里 **没有** 根目录 `.release.md` 时，作为生成 release notes 的默认骨架。
>
> 它与 **项目级** `.release.md` 是两回事：项目级 `.release.md` 由各项目自行维护，优先级更高，命中后会按其结构填充；本模板只在项目级模板缺席时兜底。

## 版本号与 tag 命名

- 必须遵循语义化版本：`vMAJOR.MINOR.PATCH`，例如 `v1.2.3`
- tag 必须带 `v` 前缀；用户输入 `1.2.3` 时由 skill 自动补 `v`
- 预发布可在尾部追加 `-rc.1`、`-beta.2` 等（如 `v1.2.0-rc.1`），并在 release 上标 `--prerelease`
- 不允许使用 `--force` 覆盖已有 tag；版本冲突时停下来让用户决定

## 默认骨架

```markdown
# Release <VERSION>

<可选：一两句话总览，说明本次发布的主题，例如「补全 /release 的模板能力」。无要点时整段删掉，不要留空标题。>

## 新功能

- <从用户视角描述新增能力，必要时点出触发方式或命令名>

## 修复

- <描述修复了什么用户可感知的问题，避免只写 commit 哈希>

## 其他改进

- <文档、依赖、内部重构里值得用户知道的部分；纯内部清理可不写>

## ⚠️ 破坏性变更

- <如有；说明影响范围 + 迁移办法。无破坏性变更时整段删除，连标题一起删>

## 📦 附件

- `<产物文件名>`：<一句话用途说明>
- 无构建附件时整段删除

## 🙏 致谢

- 感谢 @<contributor> ……
- 无外部贡献者时整段删除
```

> 生成原则：**用到哪段保留哪段；没用到的整段删除（含标题），不要留空小节或 "无" 占位**。
> 所有 `<...>` 占位符在发布前必须替换干净，自查一遍不能有残留。

## 写作要点

| 要点 | 说明 |
| ---- | ---- |
| 中文撰写 | 与本仓库 commit 风格保持一致；专有名词、命令名保留英文 |
| 用户视角 | 写"用户能感知到什么变化"，而不是"我改了哪些文件" |
| 聚焦价值 | 每条要点突出"现在能做什么 / 不再发生什么"，必要时点出触发条件 |
| 一行一事 | 一个要点只讲一件事；多个变更拆成多条 |
| 链接到位 | 如有相关 PR / Issue / 文档，行尾追加 `(#123)` 或链接 |
| 命令与路径 | 用反引号包裹，例如 `/release`、`release/assets/TEMPLATE.md` |

## 完整正例

基于本仓库历史改写（假设把 `bb5f37f`、`fefba38`、`bcda121`、`49b55f1` 几次提交合并发布为 `v0.2.0`）：

```markdown
# Release v0.2.0

本次发布完善了 `/release` 与 `/merge` 两个斜杠命令的端到端体验：release 可读取项目模板生成 notes 并上传构建附件，merge 则锁定 merge commit 策略并在合入后自动同步本地仓库。

## 新功能

- `/release` 支持读取仓库根目录的 `.release.md` 作为 release notes 模板，自动按提交记录填充版本号、功能标题等占位符
- `/release` 支持构建附件上传，先推 tag 再触发构建，确保产物里写入的版本号正确

## 修复

- `/merge` 在合入 PR 后自动 `git fetch` 并切换到目标分支，避免后续操作仍停留在过期 HEAD 上

## 其他改进

- `/merge` 强制使用 merge commit，禁用 squash / rebase，保留分支拓扑便于后续回溯

## 📦 附件

- `manage.sh`：一键安装 / 卸载脚本，可直接 `curl` 后执行
```

## 反例（避免）

- 直接粘贴 `git log --oneline` 输出，没有按"新功能 / 修复 / 其他"归类
- 用 commit 标题原文充数，例如 `- bcda121 merge 完成后自动同步本地仓库……`，把哈希也写进 notes
- 描述内部实现而非用户感知，例如 `- 重构 release.sh 的 parse_args 函数`（用户不关心内部函数）
- 标题用英文 `## Features / ## Bug Fixes`，与中文正文风格不统一
- 保留空小节，例如：

  ```markdown
  ## ⚠️ 破坏性变更

  无
  ```

  应整段连同标题一起删掉
- 占位符忘了替换，发布出去还能看到 `<VERSION>`、`<PREV_VERSION>`
- 一条要点塞多个变更：`- 修复了 A、新增了 B、还顺便重构了 C`，应拆成 3 条
- 版本号写成 `0.2.0`、`release-0.2.0`、`V0.2.0`，未遵循 `vMAJOR.MINOR.PATCH`
